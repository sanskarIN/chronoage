# ADR 0010: Cargo lockfile reproducibility transition

- **Status:** Accepted
- **Date:** 2026-09-02

## Context

ChronoAge uses Tauri 2 and Rust for its native delivery targets. The repository currently pins the Rust toolchain but does not yet contain a genuine `src-tauri/Cargo.lock`. Native builds therefore still require dependency resolution from the configured registries.

A hand-authored or inferred lockfile would provide false reproducibility. The lockfile must be generated by Cargo from the actual manifest and reviewed before native CI is changed to depend on it.

## Decision

ChronoAge will use a two-stage Cargo dependency policy:

1. **Pre-lockfile mode:** native workflows may resolve dependencies normally. Static policy checks must explicitly recognize the absence of `Cargo.lock` and must not manufacture one.
2. **Locked mode:** once a genuine `src-tauri/Cargo.lock` is committed, native verification must execute Cargo with `--locked`, and the workflow policy must require that locked verification step.
3. The locked verification uses `cargo metadata --locked` so CI can fail before a longer native build if the manifest and committed dependency graph disagree.
4. Native CI will run the same transition policy on desktop, Android, and iOS jobs.
5. The release workflow remains web-release focused; native artifact verification remains a separate evidence-gated release concern.

## Consequences

- The current repository remains buildable before the real lockfile is available.
- The transition from `cargo` resolution to locked verification becomes fail-closed rather than depending on reviewer memory.
- A genuine Cargo-generated lockfile can be introduced later without simultaneously rewriting every native workflow.
- A successful `cargo metadata --locked` check is necessary but does not by itself prove that every platform-native artifact builds successfully.

## Rejected alternatives

### Hand-author a Cargo.lock

Rejected because it would not represent a verified dependency graph and could hide resolver or transitive-dependency mistakes.

### Enable `--locked` immediately

Rejected because the repository currently has no committed Cargo lockfile; doing so would make the existing native CI fail for a known repository-state reason.

### Rely only on documentation

Rejected because the lockfile transition is easy to regress when workflow installation commands change. The repository now enforces the policy with executable checks.
